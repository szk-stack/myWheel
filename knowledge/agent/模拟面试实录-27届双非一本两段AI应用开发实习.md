# 一、项目一：复杂文档解析与 RAG 检索

## 1.1 文档解析与切分（父子块）

学员的答法：

- 用 **MinerU** 解析文档，自动分成 block，再对 block 做切分分块。
- 采用**父子块结构**：子块初始定义 **256 token**，超过这个数值就认为是长文本，做子块切片。
- **子块向量入库，父块单独存储**。
- 检索时，在重排之后的最终结果上，对**有父块的内容做归并去重**，然后直接把**父块的上下文**拼接上去。
- 切片会遇到**零散**问题，所以在切片元数据里**注入文档标题**等信息，做**元数据增强**。

（要点：父子块 = 小块检索保证精度、大块返回保证上下文完整；元数据增强是为了让孤立的切片带上来源身份，重排和回溯时能用。）

## 1.2 ★ 面试官的关键要求：必须准备一个「具体到细节」的真实 case

面试官追问：「举个具体的例子，你当时处理时问题最大的一个真实例子，一个文档是什么样的文档，你们业务里面的？」

学员答：**「这个我没有编过。」**（即没有准备过案例）

面试官的纠正（这段是全场最值钱的干货）：

1. **你写了"北美海关退换政策"这种非常真实的点，就一定要准备一个具体例子。** 这个点看起来太真实了，面试官一定会往细里问。
2. 顺着这个问题，面试官**教了怎么造一个可信的案例**：
   - 场景：跨境电商客户提供的一份**英文政策 PDF**（北美海关的退换政策）。
   - 客户要**具体到一个有名字的客户**——你们合作的某一家公司。
   - 商品要具体：可以是**硬件商品、软件商品、服装、应季产品**，配一份退换政策或商品手册。
   - **素材获取**：北美海关政策网上能爬到；商品手册这类 PDF 也能找到；找不到就**让 AI 按这个客户生成一个 PDF 当案例**。
   - **关键动作**：自己真的去**解析一遍**，看它会出什么问题——这样讲起来才真实。
3. 面试官点明面试逻辑：**「他面试重点就问这些东西」**。
   - 「如果你说得比较笼统，他可能会怀疑」；
   - 「他（面试官）觉得最有价值的就是**实际工作中有问题（的真实案例）**」；
   - 面试官「喜欢问的就是这种最具体的，想听的就是这个」。
4. 方法论：**根据业务，找 AI 编一些 bad case**，但一定要编**一个具体的例子**，并且自己跑一遍。

> 这一条可以推广到所有简历项目：**简历上敢写具体业务名词，面试就一定会被问到那个名词下面的真实细节。写之前先想好案例。**

## 1.3 检索链路

学员的答法（链路完整，可直接参考其表述顺序）：

1. **查询改写**：检索之前先做查询改写，用 **HyDE** 的形式——对用户的提问**先模拟生成一个回答**，然后把「回答 + 原提问」一起放进检索流程做召回。
2. **双路召回**：
   - **向量检索**：解决用户**口语化表达**的问题，用语义相关性召回；
   - **关键词检索**：针对用户指定的**型号**等需要精确匹配的内容，提取关键词，检索更精准。
   - 两路结果用 **RRF 融合权重**。
3. **融合后取 top30 → 精排**：用 **cross-encoder** 做精排，取 **top6~8** 放进上下文。
4. **父块回溯**：如果有子块，就索引回父块（把父块上下文带出来）。

## 1.4 指标口径：召回率 90%+、MRR 74%+ 怎么来的

面试官问的就是「这些数据是怎么出来的」。学员的回答构成了一套完整的评测体系：

**评测框架**：用 **RAGAS**，它提供了一些基础参数/指标，可以直接做评测。

**评测集三块来源**：

| # | 来源 | 做法 |
|---|---|---|
| 1 | 上线前 · 文档切片生成 | 把切好的文档里抽切片，用 **GPT / Claude** 这类较强的大模型生成「问题 + 解答」，作为**基础黄金集** |
| 2 | 上线前 · 私有语料 | 运营人员从清洗好的数据里挑出**经典的用户提问**，再挑**相关切片**，作为真实案例加入黄金集 |
| 3 | 上线后 · 线上反馈 | 前端埋点（点赞、提交工单等）、监控**转人工率**、**异常转人工的 badcase**，把这些案例提出来放进 **badcase 库**，统一进评测集 |

**上线流程**：离线跑评测 → 指标满意 → **AB 测试**放小流量 → 线上不出问题 → **逐步放量** → 更新版本。

> 这套「上线前合成 + 上线前真实语料 + 上线后 badcase 回流」的三段式评测集构建法，是这条视频里最成体系的一块，可直接照着搭。

# 二、项目二：电商导购线索沉淀

学员的答法：

- 在 **LangGraph 的 State** 里放几个**槽位**。
- 每次用户消息进来，根据上下文做**槽位提取**：提取到就填入，没有就留空。
- 最后有一个**提交节点**，写进 **PG（PostgreSQL）的 outbox 表**，由后台 **Worker 异步消费**，再写入 **CRM**。

## 2.1 ★ 面试官的纠正：架构别吹过头，会被判「太假」

学员最初的说法是「丢进 **Kafka**」，面试官直接说**太假**；退一步说「先丢 Kafka，后面多个 worker 消费再写进 SQL / 走消息队列」，仍被判**有点假**。

**判假的理由（重要，是面试官的真实判断逻辑）**：

- 他说「用户 **QPS 只有几百**」——面试官反问：你们其实挺大的公司，但做的是**跨境独立站**，不是大商城，「感觉这流量确实有点假」。
- 补刀：**「就算黑色星期五这种场景，也不会有特别高的量。」**
- 结论：**小流量场景堆 Kafka + 多 worker + 削峰填谷，是架构过度设计，面试官一眼看穿。**

**学员的补救方案**：改成「用 PG 自带的队列直接消费」，再讲一些队列相关操作。

**面试官给的正解——把「堆技术」改成讲「扩展性设计」**：

1. 如果 QPS 真不高，**不需要削峰填谷**，这一点瞒不过去。
2. 更好的说法是：现在业务是**独立站**，服务客户规模约几百个（学员自己提到「服务客户规模约 600 个」）；**后期客户可能不是独立站，而是接入到更大的电商体系里，流量就大了**。
3. 所以当时做设计时，**就考虑到了后期迁移到更大业务**，因此把 Kafka、多 worker 消费、削峰填谷这套技术都用起来了。
4. 面试官的评语：**「你在架构当时搭的时候，考虑到以后去扩展，所以把技术都用起来了，这样说可能更好。」**

> 通用结论：被质疑 QPS/流量时，**不要硬吹流量，改为讲「我当时就预判了业务会变大，所以按可扩展设计」**——这既解释了技术选型，又显出了架构判断力。

**另一处要补的**：面试官指出「**还得编一下具体的容量数据**」（多大的量、多少客户），否则数字对不上。学员还反思「这些 Redis 其实根本没啥用」，结论是**要么删掉，要么用扩展性逻辑解释它为什么在那**。

# 三、Agent 业务描述与价值量化

## 3.1 业务描述（学员答得还可以，可作为业务背景模板）

- Agent 主要起**客服**作用。
- 服务的这家公司做**广告投流**：在 **WhatsApp / Instagram / TikTok** 上投流，把用户引到 WhatsApp 或公司**独立站**成交。
- 用户进来后，Agent 可以做**商品推荐、下单、售后**。

## 3.2 ★ 价值量化是明显弱项

面试官问：「相比人工，这个 Agent 自动化之后解决了问题、产生了什么价值？效果怎样？」

学员答：**「主要就是减少了一些人工成本」**，并自己承认**「这点我也不是很清楚」**。

→ 这是全场答得最弱的一处。**Agent 项目必须能报出业务价值口径**（接待量、工单量、人工成本、转化率、响应时长之类），否则面试官会认为你只是在做技术没看效果。

# 四、实习项目：云边机器人云管服务

学员的答法：

- 与一家公司合作：对方开发机器人本体、**端侧模型**和硬件；学员方做**大规模的云管服务**。
- 通过 **WebSocket** 连接端侧模型，把模型指令**下发到端侧执行**。
- 服务还会把机器人的**状态上传到云端**，云端做**固件升级**、**健康巡检**。
- 技术栈较偏门：**KubeEdge**（「可能都没听过」），相当于对**弱网环境做加强**，解决**组网环境下的连接问题**。
- 学员坦白：这块**不是他做的**，公司主要做云管和机器人集群，他自己主要是端侧那一块，项目"挂了个名"，技术栈偏门，所以没细看。

## ★ 面试官的点评：这个项目反而是加分项

- **机器人这个点面试官会更感兴趣。**
- 简历上要把关键词写出来，比如「**弱网环境下的优化**」。
- **如果手上有代码，最好和后端结合起来讲。**
- 让学员**去把 KubeEdge 弄懂**（面试官自己也不懂，说「这个东西我不太懂，你要去弄一下」），弄懂了就大胆写上去。

> 判断：**冷门技术栈 + 硬件/机器人场景，反而是差异化优势**——面试官见得多的是 RAG，见不到的是 KubeEdge 云边协同。别因为"不是我主做的"就整段砍掉，而是把能讲清的部分写出来。

# 五、简历修改建议（逐条）

面试官对着简历一条条给的意见：

1. **流水线安全脱敏：不要单独列成一个点。**
   - 理由一：它毕竟只是一条流水线，**站位置太多**；
   - 理由二：**「这块就没人问」**，数据这块没人问；
   - 做法：**融合到其他点里**，当成数据处理里的一个子点讲。
2. **项目一的问题点合并**：第一、第二点合到一起，第三点接在后面。**字数也别太多**，方便面试官看到后面的项目。
3. **给后面的项目留位置**：项目一占位置太多，要**收缩**；第二个项目（实习）"性价比"更高，要留足篇幅。
4. **项目二线索沉淀保留**，但要**跟后端 CRM 结合**，加后端的词（加密、队列处理这类），因为写入那一步本来就是后端动作。
5. **记忆模块保留**，且「写入」这一步的**后端细节要写得更清楚一点**。
6. **★ 项目一的通病（技术类回答的普遍问题）**：
   - 学员自述：「我 RAG 回答的时候，我都懂，但**我一回答就是通用东西，没回答真实的 case**。」
   - 面试官的答法：**想一个 case 背下来**——「你可以说当时我们有一个什么样的东西，它召回没召回到，是什么问题，我们当时怎么优化的，就这样去说。**那个点就想一个例子，背那个例子就好。**」
   - 即：面试不是讲原理，是**讲你踩过的那个具体坑**。
7. 整体评价：简历「东西还可以」，主要问题在**投递量**，不在简历质量。

# 六、求职策略

## 6.1 投递量与学历现实

- 学员的问题：**只投大厂、小公司投太少**。
- 面试官判断：**学历会吃亏**——「可能需要一个 **985 / 211 硕士**的学历，或者**大厂实习**经历，大公司才更愿意给面试机会」。
- 建议：**Boss 上广投**，小公司也投。
- 时间点：**秋招一般 12 月底结束**。

## 6.2 ★ 一个很实用的技巧：简历/打招呼里写明「人在浙江，可线下面试」

面试官的原话逻辑：

- **很多小公司不接受线上面试**，所以只投线上会漏掉一批机会。
- 做法：在 Boss 打招呼时就写「**我人在浙江嘉兴，如果需要我可以来线下面试**」。
- 效果：**「这样他其实机会更多点。」**
- 因为 HR 看你在外地（比如学校在长春），会**默认你不会来，直接不给面试**。
- 可覆盖城市：**杭州、上海、南京**（浙江及周边，距离都可接受）。
- 在线简历的**个人信息里也可以加一个浙江**。

## 6.3 线下面试的实际流程

- 流程和线上**差不多**，主要是**问简历**，可能让你写笔试题。
- 这类岗位（AI 应用开发）**笔试一般比较少**，「这块没什么笔试可写的」。
- 面试官半开玩笑的实话：真要笔试，很多公司也不看你写的，可以拍照用大模型搜——但强调这种情况**比较少**。

# 七、可复用的检查清单（从这期提炼）

对着自己的简历和项目，逐条自问：

- [ ] 简历上写的每一个**业务名词**（如"北美海关退换政策"），我有没有一个**具体到客户名、文档类型、出了什么问题、怎么修**的案例？
- [ ] RAG 项目能不能报出**指标口径**：指标是什么、评测集怎么来的、用什么框架算的？
- [ ] 架构里的每个中间件（Kafka / Redis），如果 QPS 不高，我能不能用**扩展性预判**解释它为什么存在？容量数字编得圆吗？
- [ ] Agent 项目的**业务价值**能不能量化（不只是"省了人工成本"）？
- [ ] 有没有一个**冷门但能讲清**的技术点做差异化（KubeEdge、弱网优化这类）？
- [ ] 每个项目在简历上**占多少行**？最值得被问的项目有没有留够位置？
- [ ] 投递时有没有写清**所在地 + 可线下面试**？
