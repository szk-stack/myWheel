## 一句话概括

DeepSeek 的 Super-agent 不是一个"更聪明的单 agent"，而是把 agent 从**一次性的、需要人开新会话并盯着的任务**，改成**跨会话连续、多实体并行的常驻实体**，拆开来是五个模块。

## 它解决的真实场景

线上出了个 bug，没人 @ 它，也没有人给它开新会话，几分钟后它自己复现、定位、把修 bug 这件事推进下去。

视频给这类能力的定位是：对找工作、对学习 agent 工程都有参考价值——因为它展示的是"agent 怎么在没有人类触发的情况下持续工作"。

## 和主流 agent 的架构区别

**主流做法：以单个会话（session）为单位，一个任务一个会话。**

人的带宽是瓶颈：一个人通常只能跟进 3~5 个会话，再多就看不过来了。所以单会话模型本质上是"人在轮询 agent"。

**Super-agent 的解法：把会话变成连续的实体。**

- 会话不再是"一次性、人手动开、人盯着"的东西，而是连续存在的实体；
- 跨会话保留上下文（换一个会话，前面的上下文不丢）；
- 可以同时推进多个这样的实体。

这是整个设计的出发点，后面五个模块都是为它服务的。

## 五个模块

### 模块一：双栈架构 —— 常驻 Router + Worker

结构上分两层：

- **上层是 Router（常驻）**：所有人类交互先接到这里，Router 只做分发——把任务派给下面的 Worker。
- **下层是 Worker**：真正去完成任务的一层。

**关键点：Router 非常非常轻。** 视频特别强调它和多 agent 的主管型（supervisor / orchestrator）架构不是一回事：

| | 主管型多 agent | 这里的 Router |
|---|---|---|
| 职责 | 制定计划、验收结果、协调各 agent | 只做分发 |
| 重量 | 重，本身也是个 agent 在思考 | 轻，常驻 |
| 模型 | — | 配最强的模型 |

也就是说：指挥层不承担推理复杂度，用最强模型保证"派活派对"，重活全压给下面。

### 模块二：主动性 —— 靠 Trigger 实现

这是"没人 @ 它也会动"的来源。用触发器（Trigger）机制驱动：先**把噪音筛掉**，只把真正有用的信号筛下来（原话是"把那些噪音都筛下来，筛下真正有用的"），再触发 agent 行动。

要点是：主动性不是"什么都响应"，而是**先过滤，再触发**——否则常驻 agent 会被无效信号淹掉。

### 模块三：上下文 —— 当缓存来放

上下文按**缓存**的思路处理。视频里对这块只给了一句，没有展开具体策略。

### 模块四：和人怎么说话 —— 改成异步

传统 agent 的问题是**同步阻塞**：工具还在跑的时候，它接收不了新消息，你说的话其实是**排队**发给它，它可能要等。

改成异步之后，人可以在 agent 干活的过程中继续插话，不必等这一轮工具调用结束。常驻、多会话并行的前提，就是通信必须异步。

### 模块五：一直在线 —— 无状态计算 + 看门狗

两层保障：

1. **计算层无状态、放云端**：会话状态放数据库，容器随时重启、随时替换，进程挂了不丢上下文。
2. **看门狗（watchdog）**：一层长期在线的监控，保证它活着、监控它运行正常。

"一直在线"不是靠一个不重启的进程，而是靠**状态外置（会话入库）+ 容器可随意重启替换 + 外部看门狗**这套组合。

## 整体结构速记

```
人类交互
   ↓
Router（常驻 / 极轻 / 最强模型 / 只分发）
   ↓
Worker（干活）
   ↑
Trigger（筛噪音 → 主动触发）
会话状态 → 数据库（无状态计算，容器随时重启替换）
Watchdog（长期在线监控）
```

五个模块串起来就是：**轻 Router 分发 + Worker 执行 + Trigger 主动触发 + 上下文当缓存 + 异步通信 + 无状态常驻**，共同支撑"跨会话连续的 agent 实体"。

## 转写存疑处（引用前请核对原视频）

- "把一次性和人动手的会话解法，变成个连续的实体"——后半句"我们同时推多的实体，连续高效组都实际"转写含糊，按上下文理解为"可同时推进多个实体"。
- 模块三"上下文当成缓存来放"原话只有一句，具体缓存什么（KV cache？上下文分块？）视频未展开，此处不臆测。
- 模块二"它把那些噪音都筛下来，筛下真正有用的"——"筛下来"应为"筛掉"的意思。
- 视频结尾提到这些点"还有很多可以说的，纯技术的东西"，说明这只是概览，不是完整技术细节。
