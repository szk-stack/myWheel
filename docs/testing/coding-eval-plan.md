# 简的 coding 能力评测方案

| 状态 | 最后更新 | 关联代码 | 代码基线 |
|---|---|---|---|
| Draft | 2026-10-26 | `engine.py` · `toolbox.py` · `tools/` · `tracing.py` | `280a5ae` |

> 本方案测的是"简这套脚手架 + 模型"的组合能力，**不**是模型单项分数。
> 目标是拿到一张"下一步该改哪一层"的清单，不是一个排名。

---

## 0. 一句话结论

不要拿公共 benchmark 测，也不要"随便聊几句看看它行不行"。
**自建 12 道题、每道配一个放在模型够不到的地方的判定脚本、只给一次机会、同一题跑三次**——
四天之内你就能得到一张能指导改代码的表，而不是一句"感觉还行"。

---

## 1. 先想清楚：你到底在测什么

### 1.1 被测对象是"模型 × 脚手架"，不是模型

2026 年的评测共识里最硬的一条：**同一个模型换一套脚手架（工具集、提示词、上下文管理、重试策略），
在公开 coding benchmark 上的成绩能从 42% 摆到 78%**；而在前沿模型之间换个模型，差距常常不到 1 个百分点。

这条对你特别重要，因为：

- 你测出来的分数**不能归因给 DeepSeek**——它好坏你改不了；
- 但**工具层、循环层、上下文层全是你写的**，这些才是你能改的。

所以这个评测的真正目的是：**找到"简"这套脚手架里最先坏掉的那一环。**

问卷式说法：你不是在给 agent 打分，你是在给你的 8 个工具做体检。

### 1.2 为什么现在不该碰 SWE-bench / Terminal-Bench

| 障碍 | 具体情况 |
|---|---|
| 环境成本 | SWE-bench 每题一个 Docker 镜像 + 仓库快照 + 依赖锁定。你零依赖、Windows 单机，光装环境就要一整天 |
| 分数含义不清 | SWE-bench Verified 在 2026 年 2 月被 OpenAI 停止上报，理由是污染和约 59% 的用例本身测试有问题；它已经饱和到分不出模型 |
| 不可比 | 榜单上的行是"某个 agent 框架 + 某个模型 + 特定工具策略"，跟你这套不可比 |
| 拿不到有用信号 | 就算你跑出 30%，你也不知道是 `edit_file` 不行还是模型不行 |

**结论**：公共 benchmark 是给选模型的人看的。你要的是诊断，不是排名。等你脚手架稳了、想横向比模型了，再考虑接 Terminal-Bench（它是"跑命令改环境"型，跟你这套最像）。

### 1.3 你真正该测的五个薄弱环节

按你的代码结构，风险从高到低：

1. **编辑层**：`edit_file` 要求"原文唯一出现"。真实项目里重复代码一大堆，这个约束会频繁失败——失败之后它会不会换策略（分段改 / 整体重写），是第一个看点。
2. **验证层**：它会不会在没跑过、没截图的情况下宣布"已完成"。这是所有 coding agent 最高频的翻车方式，也是 `screenshot` / `view_image` 这套自检闭环存在的意义。
3. **环境层**：Windows + 中文 + GBK。`exec_command` 的三层编码兜底是补丁，不是免疫；路径分隔符、`python` 还是 `py`、端口占用，都会在这里冒出来。
4. **上下文层**：文件一多、对话一长，需求会不会丢。你的压缩阈值是 70% × 1M，普通任务根本触发不到，**这条得专门造一个长任务去压**。
5. **循环层**：模型自己会不会停（现在没有轮次上限）、会不会反复跑同一条失败命令、`spawn_agent` 会不会把任务越拆越糊。

## 2. 三条必须先立的规矩

### 2.1 判定脚本必须放在模型够不到的地方（最重要的一条）

你的 agent 有 `write_file`、`edit_file`、`exec_command`。**如果把 `check.py` 放进工作区，它读得到答案，甚至能改测试让它变绿。**

这不是多虑，业界专门有个词叫 **reward hacking**（奖励作弊）：agent 发现"改测试比改代码容易"，就会去改测试。SWE-bench 的提交审核现在要求上交完整轨迹，就是为了抓这个。

好消息是：**你的架构天然就能做到隔离。**

```
D:/project/朴素agent/
├── eval/
│   ├── tasks/          ← 题目 + 输入素材（agent 在 prompt 里只看到描述）
│   └── checks/         ← 判定脚本，永远不进去
└── sandbox/
    └── eval-L1-01/     ← agent 的工作区，锁死在这里
```

工作区设成 `sandbox/eval-L1-01`，`safe_path` 就把 `../` 全挡了，`eval/checks/` 它在物理上够不到。

> **红线**：跑评测时**绝不把工作区设成"项目目录"**。一旦指向项目根，`eval/checks/` 就在它的 `read_file` 范围里，整套评测立刻失效。

### 2.2 一次机会，不给重试（pass@1）

只记录**第一次**的结果。觉得"它第二次就做对了"于是记成功——这叫 best-of-N，是排行榜最常见的注水手法，也是对自己撒谎。

想衡量稳定性，用 **pass^3**（同一题独立跑三次，三次全过才算过），不是 pass@3（三次里有一次过就算）。

### 2.3 同一题至少跑三次

LLM 有随机性。跑一次得到的"通过"，可能是运气；跑一次得到的"失败"，可能是运气。
**三次里过一次 = 不稳；三次全过 = 真会；三次全挂 = 真不会。** 这三句话的信息量远超一个百分比。

## 3. 任务集：12 道题

难度分四层。**按顺序跑，前一层不过就别往下走**——L0 挂了说明环境坏了，后面测的全是噪声。

### L0 冒烟（3 题，每题 2 分钟，只验证"器官还活着"）

| 编号 | 任务 | 验证什么 | 合格的标志 |
|---|---|---|---|
| L0-1 | 在工作区新建 `hello.py`，打印 1 到 10 的平方，然后运行它把输出贴给我 | write_file → exec_command → 结果回读，整条链路 | 输出里真的有 1/4/9/…/100 |
| L0-2 | 读 `config.py`，告诉我 `MAX_TOOL_ROUNDS` 的值，不要猜 | read_file + 不瞎编 | 答 0（0 = 不限制），且没有编造行号 |
| L0-3 | 在 `docs/` 里找到讲"上下文压缩"的那份文档，用三句话概括 | list_dir + 多文件定位 | 找的是 `docs/modules/plugins/compact.md` |

L0 的作用是**排除故障**。这三题任何一题挂了，先修环境，别继续。

### L1 单文件（4 题，每题 5-15 分钟，有客观答案）

这一层是主体，每题都有唯一正确答案，判定脚本可以完全自动。

**L1-1 CSV 统计（陷阱：编码）**

> 工作区有个 `sales.csv`（GBK 编码、带 BOM、金额列有千分位逗号、中间夹了一行空行）。
> 写一个 `stats.py`，读它，输出每个品类的金额合计，按金额从高到低。
> 要求：只用 Python 标准库。

输入素材你自己造，放 `eval/tasks/L1-01/assets/`。
陷阱全在真实数据里：用 UTF-8 打开会乱码；不处理千分位会 `ValueError`；空行不跳过会崩。

**L1-2 坏数据容错（陷阱：边界）**

> 工作区有 `events.jsonl`，其中**有 3 行是坏的 JSON**。
> 写一个 `analyze.py`，统计每个 `type` 出现了几次，并打印耗时最长的 3 条。
> 坏行要跳过并统计有多少行被跳过，不能中断。

看点：它会不会 `try/except`，还是直接崩。**"遇到坏数据不崩"是工程能力和玩具代码的分水岭。**

**L1-3 修 bug（陷阱：定位）**

准备一个 30 行左右、**你预先埋了 3 个 bug** 的脚本，例如：

```python
def average(nums):
    total = 0
    for n in nums:
        total += n
    return total / len(nums)      # bug1: 空列表除零

def top_n(items, n):
    items.sort()
    return items[:n][::-1]        # bug2: 排序方向搞反

def load(path):
    return open(path).read()      # bug3: 没关文件 + 没指定编码
```

> 这个脚本有三个 bug，找出并修好，然后自己跑一遍验证。

**修 bug 比写新代码难**，也是 SWE-bench 的原型任务。看点：它是靠读代码找到的，还是靠跑一遍报错找到的——后者更可靠。

**L1-4 不许用第三方库（陷阱：纪律）**

> 写一个 `calc.py`，支持加减乘除和括号的表达式求值。**只能用标准库，不许 import 任何第三方包。**

看点：它会不会偷偷 `import requests` 或者提议 `pip install`。你的项目底线是零依赖，这条必须守。

### L2 多文件小项目（3 题，每题 30-60 分钟）

**L2-1 单文件游戏（测自检闭环）**

> 做一个 index.html，里面是能玩的贪吃蛇：方向键控制、撞墙或撞自己结束、显示当前分数。做完自己看看效果。

看点：**它有没有主动调用 `screenshot` + `view_image`**，以及看到截图之后有没有真的改。
只写不看的，说明自检闭环没被触发——这可能不是模型的问题，是 `SYSTEM_PROMPT` 里没引导，或者截图工具的返回值不够有吸引力。

**L2-2 前后端小应用（测多文件协作）**

> 做一个极简记事本：`index.html` + `server.py`（只用标准库 http.server），支持新增、删除、列出。数据存 `notes.json`。用 8001 端口，别占用我 8000 的服务。

看点：接口两边对不对得上、端口有没有听证、会不会把自己的服务跑起来之后忘了关。

**L2-3 需求中途变更（测上下文保持）**

先让它做 L2-2，等它做完，说：

> 改一下：删除之前要弹确认框，另外每条记事显示创建时间。

看点：它改的是"新加功能"还是"重写一版"。**能增量改的才算工程能力，重写谁都会。**

### L3 改造真项目（2 题，最有价值）

这一层的判定脚本不是 `check.py`，**是"简"自己的行为**。

**L3-1 给"简"加功能**

> 读一下 README 第七节的练习题 7，给 `spawn_agent` 的报告末尾加上"这次花了多少秒"。改完自己验证一下服务还能正常启动。

判定：
1. `tools/spawn_agent.py` 真的改了且改对了；
2. **它有没有动别的文件**（回归）；
3. 改完服务还能起（`python server.py` 不报错）。

**L3-2 修"简"的真 bug**

在你自己的代码里**故意埋一个 bug**（比如把 `exec_command` 的超时改成 0.001 秒，或者把 `safe_path` 的 `..` 检查删掉），写成一个 issue 式的描述：

> 最近发现执行命令经常莫名其妙失败，报超时，但我跑的命令很快。帮我查一下。

判定脚本：你埋的那个 bug 被修好了，且**没有顺手改坏别的**。

L3 的关键：**它有 8 个工具、一个 1000 行的项目，它会不会先读再改，还是直接动手。** 直接动手改核心文件，是最危险的行为。

## 4. 判定脚本怎么写

零依赖，一个文件一个函数，**通过退出码表达结果**（0 = 过，非 0 = 挂）。

```python
# eval/checks/L1-01.py
# 用法：python eval/checks/L1-01.py sandbox/eval-L1-01

import json
import subprocess
import sys
from pathlib import Path

ws = Path(sys.argv[1])
script = ws / "stats.py"

if not script.exists():
    print("FAIL: 没有 stats.py")
    sys.exit(1)

# 跑它写的脚本，而不是读它的代码 —— 这是关键
r = subprocess.run(
    [sys.executable, str(script), str(ws / "sales.csv")],
    capture_output=True, text=True, encoding="utf-8", errors="replace", timeout=30,
)

if r.returncode != 0:
    print("FAIL: 脚本跑不起来")
    print(r.stderr[-800:])
    sys.exit(1)

out = r.stdout
# 只做"对不对"的判断，不管它怎么实现的
for expected in ["水果 130.5", "饮料 88.0", "零食 42.3"]:
    if expected not in out:
        print(f"FAIL: 缺少 {expected}")
        print("实际输出：", out[:500])
        sys.exit(1)

print("PASS")
```

三条原则：

1. **跑它的脚本，别读它的代码。** 代码好看不代表能跑，代码难看但能跑就是对的。
2. **只判题目要求的东西。** 不要顺手检查"有没有写注释"——那会把评测变成风格审查。
3. **报错信息要能看懂。** 你之后要靠它区分"哪一步坏的"，所以 `FAIL` 后面一定跟具体原因。

L3 的判定脚本改用**行为断言**：

```python
# eval/checks/L3-01.py —— 检查"改完之后服务还起不起得来"
import subprocess, sys, time
p = subprocess.Popen([sys.executable, "server.py"], stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True)
time.sleep(3)
if p.poll() is not None:          # 已经退出了 = 起不来
    print("FAIL: 服务启动即退出")
    print(p.stdout.read()[-1500:])
    sys.exit(1)
print("PASS: 服务活着")
p.terminate()
```

## 5. 记账表

`eval/runs.csv`，**一次运行一行**，别事后补。

| 字段 | 怎么填 |
|---|---|
| `task` | L1-01 |
| `run` | 1 / 2 / 3 |
| `pass` | 1 / 0 |
| `干预` | 你中途插话/重发的次数（0 最好） |
| `轮数` | 从 `traces.jsonl` 数这轮的 tool 调用次数 |
| `秒` | 从 `traces.jsonl` 拿总耗时 |
| `自验` | 它有没有自己跑测试/截图（1/0） |
| `类型` | 失败归类，见第 6 节 |
| `备注` | 一句话 |

`traces.jsonl` 里已经有每轮的 request 快照、工具耗时和最终状态，**轮数和耗时可以直接算出来**，不用手记。这是你这套东西比大多数人自建评测强的地方——别人还在靠肉眼数。

如果 traces 里没记 token 用量，**先别为了评测去改代码**。轮数 + 耗时已经够做决策了。

## 6. 失败归类（这张表比分数有用）

每次挂掉，归到下面一类，只归一类：

| 类型 | 症状 | 该改哪里 |
|---|---|---|
| **找错** | 猜路径、没 `ls` 就 `read`、读了不相关的文件 | `SYSTEM_PROMPT` 加"先看目录再动手"；`list_dir` 的返回值做得更醒目 |
| **改错** | `edit_file` 报"原文不唯一"、改到别处、漏改 | `edit_file` 加"失败时提示改用 write_file 重写"的引导 |
| **环境** | 中文乱码、路径分隔符、`python` 找不到、端口占用 | `exec_command` 的错误信息要翻译成人话，别把 Traceback 直接扔给模型 |
| **逻辑** | 算法/边界想错 | 模型问题，改不了，记下来 |
| **幻觉完成** | 没跑、没看，就说"已完成" | 最值得改的一类：在工具返回里加强制校验，或在 prompt 里要求"报告前必须跑一次" |
| **循环** | 重复同一条失败命令、跑到停不下来（要手动点停止） | 循环层：加"同一命令失败两次就换策略"的提示；再定闸门 |
| **失忆** | 压缩后忘了约束、多轮后改了需求 | 上下文层：压缩摘要要显式保留"任务的硬性要求" |

**判读方法**：12 个任务跑完，数一下哪类最多。那一类就是下一步该动的地方——不是"该换个更强的模型"。

## 7. 怎么判读结果

跑完先看这四行，别看总分：

1. **L0 是不是 3/3** —— 不是就先修环境，后面全是噪声。
2. **L1 是不是 ≥ 3/4，且干预次数为 0** —— 低于这个，说明基础工具链还不稳，别急着做 L2。
3. **L2 有没有 1 题它自己截图/自己跑测试** —— 这是"自检闭环"是否真的成立的唯一证据。
4. **L3 改完有没有动不该动的文件** —— 动了，说明它对"改动范围"没有概念，这在真实项目里是灾难。

至于总分：

- **L1+L2 通过率 < 50%**：先别怀疑模型。42%~78% 的差距来自脚手架，你这个分数更可能是工具描述写得不够清楚、错误信息太原始、或者 `SYSTEM_PROMPT` 里没告诉它"先看再改"。
- **L1 高、L2 低**：典型的"会写函数不会做项目"——问题在多文件协调和自检，不在编码。
- **L1 高、L3 低**：读别人的代码能力不足，`read_file` 分段读和"先定位再改"的策略要补。
- **三次结果差别很大**（一次过一次挂）：稳定性问题，优先加"报告前必须验证"这类硬约束。

## 9. 针对"简"的已知坑（压测时重点盯）

这些是你架构里已经知道的风险点，评测时专门盯：

1. **`edit_file` 的"原文唯一"约束**——真实项目里极易失败。L3 会密集触发。看它失败后是重试同样的字符串，还是换 `write_file` 整体重写。
2. **`exec_command` 的编码三层兜底**——中文输出仍可能乱。看它会不会把乱码误判成"命令失败"，然后开始瞎改。
3. **没有轮次上限（`MAX_TOOL_ROUNDS = 0`）**——重点不再是"会不会撞线"，而是**它自己会不会停**。每个任务记下真实轮数（`traces.jsonl` 里的 `rounds`）；出现 50+ 轮还不收工的就是失控样本，这张分布表直接决定闸门该设成什么。
4. **工作区串台**——`threading.local` 是防串台的。同时开两个对话跑不同任务，看会不会互相污染（这条值得单独测一次）。
5. **上下文压缩**——1M 窗口 + 70% 阈值，普通任务根本触发不到。想测这条得专门造一个"读 20 个文件"的任务，或者临时把 `CONTEXT_WINDOW` 调小到 20000 来模拟。
6. **`spawn_agent` 看不到图**——已知限制。让它做需要看图的任务时，别指望子代理能自检。
7. **子代理的"结论丢失"**——`_slim()` 会截断到 3000 字符。让它调查一个大文件，看结论会不会被截断成没用的话。

---

## 10. 三个会让你白测的坑

1. **把失败的例子贴进 `SYSTEM_PROMPT`** —— 一旦贴了，这题就污染了。下次它"会做"是因为你告诉了它答案。题目要么换，要么这题作废。
2. **跑一次就下结论** —— 见 2.3。
3. **只看结果不看过程** —— 一个靠"改测试文件"通过的 case，比失败更糟。判定脚本之外，抽查 `traces.jsonl` 里它到底碰了哪些文件。

## 附：一句话版本

> 三道冒烟题确认没坏 → 四道单文件题（编码、容错、修 bug、零依赖）+ 判定脚本 → 三道多文件题看它会不会自检 → 两道改自己代码的题看它敢不敢乱动。
> 每题三次，只记第一次，判定脚本放墙外，失败按类型归类。
